MODULE RESPONSIBILITY

Module 9 combines document text, embeddings, and metadata into searchable records. Module 7 computes the embeddings, Module 8 prepares the database, and Module 9 writes and maintains the corpus contents.

The module is responsible for validating records, using deterministic IDs, performing batch upserts, verifying stored data, and publishing a corpus only after all required checks are completed.


1. MODULE PURPOSE

Module 9 is responsible for storing processed document text, embeddings, and metadata as searchable records in Qdrant.

Module 7 generates the embeddings, Module 8 prepares the Qdrant database and collection, and Module 9 handles the actual storage and maintenance of the corpus.

The main purpose of this module is to make sure that only valid and complete records are stored in the vector database. It also handles repeated ingestion, updates, deletion, verification, and safe publishing of new corpus releases.


2. DATA STORED IN QDRANT

A searchable record in Qdrant mainly contains three parts:

Document Text

The text or chunk that can be retrieved when a user asks a question.

Embedding Vector

The numerical representation of the document text generated by the embedding model. This vector is used for semantic similarity search.

Metadata

Metadata contains additional information about the document, such as document ID, chunk ID, source file, page number, section, version, or corpus release.

These three components work together to create a searchable Qdrant point.

Document Text + Embedding Vector + Metadata
                    ↓
            Searchable Qdrant Point


3. RECORD VALIDATION

Before a record is stored in Qdrant, it should be validated.

The validation process checks that the document text is present, the embedding exists, the vector has the expected dimensions, the point ID is valid, and the required metadata fields are available.

The record should also belong to the correct corpus release.

Invalid or incomplete records should not be silently inserted into the database. They should be rejected or reported so that the problem can be corrected.

This validation step is important because incorrect records can affect retrieval results and make problems difficult to identify later.


4. DETERMINISTIC POINT IDS

Each Qdrant point should have a stable and deterministic ID.

A point ID can be created using information such as the document ID and chunk ID.

Document ID + Chunk ID
          ↓
    Stable Point ID

The same document chunk should receive the same ID whenever it is processed again.

This provides idempotent ingestion. If the same record is uploaded again with the same point ID, Qdrant overwrites the existing point instead of creating a duplicate.

For example:

First ingestion:
Document A, Chunk 1 → ID 101

Second ingestion:
Document A, Chunk 1 → ID 101

The second operation updates the existing point rather than creating another point.

This means that running the ingestion process twice does not create duplicate records when stable IDs are used.


5. BATCH UPSERT

After validation, the records are written to Qdrant using batch upsert operations.

The general process is:

Validate records
      ↓
Create Qdrant points
      ↓
Group points into batches
      ↓
Upsert into Qdrant
      ↓
Wait for completion
      ↓
Verify stored data

Batching makes the ingestion process more efficient because multiple records can be written together instead of performing a separate operation for every document chunk.

Only validated records should be included in the batches.


6. WRITE COMPLETION AND VERIFICATION

Validation of the stored collection should happen only after the database writes have completed.

The correct order is:

1. Validate the input records.
2. Upsert the records into Qdrant.
3. Wait for the writes to complete.
4. Verify the number of stored points.
5. Check sampled payloads.
6. Compare the stored data with the corpus manifest.
7. Publish the release only after all checks pass.

This prevents a partially written collection from being treated as a successful ingestion.


7. STORED COUNT VERIFICATION

After ingestion, the expected number of records should be compared with the number actually stored in Qdrant.

Example:

Expected points: 5,000
Stored points:   5,000
Result: PASS

If the numbers are different, the release should not be published until the reason for the difference is understood.

Count verification helps identify missing records or incomplete ingestion.


8. SAMPLE PAYLOAD VERIFICATION

Checking only the total number of points is not enough.

A collection may contain the expected number of points while still having incorrect text or metadata.

Therefore, a representative sample of stored points should be checked.

The sampled records can be verified for:

Point ID
Document ID
Chunk ID
Text
Metadata
Embedding information
Corpus release information

This helps confirm that the data was stored correctly and that the payload structure is consistent with what the application expects.


9. CORPUS MANIFEST

The corpus manifest describes the expected contents of a corpus release.

It can contain information such as:

Corpus version
Number of documents
Number of chunks
Expected point count
Document identifiers
Embedding model and version
Vector dimensions
Release information

The manifest provides a reference for checking the data stored in Qdrant.

For example:

Corpus Release: v2
Documents: 100
Chunks: 5,000
Expected Points: 5,000

The stored collection should match these expected values.

The corpus manifest must match the actual stored data before the release is published.


10. UPDATES AND DELETION

Documents can change over time. A document may be updated, removed, or replaced by a newer version.

Instead of directly changing the currently active collection in an unsafe way, Module 9 should create a new versioned collection for a new corpus release.

For example:

rag_corpus_v1
rag_corpus_v2
rag_corpus_v3

Each version represents a complete corpus release.

The new version can be built and verified without affecting the collection that is currently being used by the application.


11. VERSIONED COLLECTION WORKFLOW

The workflow for a new release is:

Create new versioned collection
          ↓
Prepare current corpus
          ↓
Validate records
          ↓
Batch upsert records
          ↓
Wait for writes
          ↓
Verify record count
          ↓
Verify sampled payloads
          ↓
Verify corpus manifest
          ↓
Publish release
          ↓
Switch active alias

The new collection should not become active until all required checks have passed.


12. HANDLING REMOVED DOCUMENTS

When a document is removed, the new corpus release should be created from the current valid corpus.

For example:

Release v1:
Document A
Document B
Document C
Document D

If Document C is removed:

Release v2:
Document A
Document B
Document D

Document C should not be available for retrieval from the new active release.

The same approach can be used when a document is superseded by a newer version.


13. QDRANT ACTIVE ALIAS

The application can use a stable Qdrant alias instead of directly using a specific collection version.

For example:

rag_active → rag_corpus_v1

After the new release has been completely verified:

rag_active → rag_corpus_v2

The application continues to use the same active alias.

Qdrant supports atomic alias changes, which allows the active collection to be switched safely.

This means the new collection can be prepared and verified before it becomes the collection used by the application.


14. SAFE PUBLICATION

A corpus release should be published only after the ingestion and validation process is complete.

The release process is:

Build
  ↓
Validate
  ↓
Verify
  ↓
Publish
  ↓
Switch Active Alias

If the validation fails, the new collection should not become active.

The existing active collection can continue serving the application until a valid new release is ready.


15. ROLLBACK

Versioned collections also provide a safe rollback mechanism.

For example:

Before release:
rag_active → rag_corpus_v1

After successful release:
rag_active → rag_corpus_v2

If a problem is discovered in version 2, the alias can be switched back:

rag_active → rag_corpus_v1

The previous release should be kept available for rollback and can be removed later according to the retention policy.

This ensures that a known-good corpus remains available if a new release has an unexpected problem.


16. EMBEDDING MODEL CHANGES

Embeddings are generated using an embedding model. If the model changes, the vectors generated for the same text may also change.

Therefore, embedding model changes need to be coordinated between the ingestion pipeline and the query application.

A typical process is:

New embedding model
        ↓
Generate new embeddings
        ↓
Create new Qdrant collection
        ↓
Validate new vectors
        ↓
Deploy compatible query embedder
        ↓
Switch active alias

The query embedder must be compatible with the embeddings stored in the active collection.

Changing the Qdrant database alias alone does not update the application code.


17. INTERRUPTED INGESTION

Ingestion can be interrupted because of application errors, database problems, network failures, invalid records, or system shutdowns.

An interrupted ingestion should not make the current production corpus unusable.

For example:

Current:
rag_active → rag_corpus_v1

New ingestion:
rag_corpus_v2

If ingestion of version 2 is interrupted, version 2 should not be published.

The active alias remains:

rag_active → rag_corpus_v1

The previous release therefore remains usable while the new release is fixed or rebuilt.

The complete workflow can be summarized as:

19. ACCEPTANCE CRITERIA

Module 9 is successful when the following conditions are satisfied.

1. Idempotent ingestion

Running the same ingestion process twice does not create duplicate points.

2. Correct updates

Updated documents are correctly represented in the new corpus release.

3. Correct deletion

Removed or superseded documents are absent from the new active release.

4. Manifest consistency

The corpus manifest matches the data stored in Qdrant.

5. Successful validation

A new release becomes active only after record counts and sampled payloads have been verified.

6. Safe interruption

If ingestion is interrupted, the previous active release remains usable.

7. Rollback support

The previous release is retained until the new release is confirmed to be stable.

8. Embedding compatibility

The query embedding model is compatible with the embeddings stored in the active collection.


20. SUMMARY

Module 9 is the storage and corpus-release stage of the RAG pipeline. It takes the embeddings generated by Module 7 and stores them with document text and metadata in the Qdrant database prepared by Module 8.

The important principles of this module are validation, deterministic IDs, batch upserts, verification, versioned collections, safe alias switching, and rollback support.

Using these practices makes the ingestion process reliable and repeatable. It also ensures that an incomplete or failed ingestion does not replace a working corpus and that the active RAG system always uses a verified collection.
